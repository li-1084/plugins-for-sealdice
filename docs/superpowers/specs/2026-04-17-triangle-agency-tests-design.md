# Triangle Agency Tests Design

## 背景

`Triangle Agency` 当前最大的风险不在单个指令说明，而在多阶段流程状态本身：

- 属性检定与非属性检定分流
- `过载` 在 QA 前就已经介入计算
- `三重升华` 会让流程跳出普通 QA
- `QA` 会跨多条指令持续存在
- 新投掷会打断旧状态，并尝试结算旧状态的混沌

这类问题很难靠手工试几次完全覆盖，也不适合只靠类型检查发现。因此这里优先为 `Triangle Agency` 设计一套“轻量自动化流程测试”方案。

## 目标

在不把整个插件全面重构成模块化工程的前提下，为 `Triangle Agency` 建立第一批可自动回归的流程测试，优先覆盖最容易出 bug 的状态机和资源结算逻辑。

这套测试应满足以下目标：

- 能自动验证 `QA`、`三重升华`、`过载`、`混沌` 的核心路径
- 不要求完整模拟整个 SealDice 运行时
- 对现有单文件脚本结构改动尽量小
- 为后续继续补更多测试留出扩展空间

## 不采用的方案

### 方案 A：只写手工测试清单

优点：

- 上手最快
- 不需要改任何代码结构

缺点：

- 不能自动回归
- 最容易漏掉“打断旧状态”和“混沌落账”这类边缘问题

结论：

不作为首选，只适合作为自动测试之外的补充。

### 方案 B：完整模拟 SealDice 环境

优点：

- 最接近真实使用方式
- 可以按真实聊天指令驱动插件

缺点：

- 需要先补很重的 `seal` runtime mock
- 当前仓库还没有测试基建，第一步就上完整模拟成本过高

结论：

暂不作为第一阶段目标，后续如果需要高保真集成测试再考虑。

## 采用方案：轻量自动化流程测试

### 核心思路

先把 `Triangle Agency` 中最核心、最容易出错的流程逻辑提取到一个可测试的“小核心”里，再用一个很薄的 fake runtime 去驱动这部分逻辑。

这里的“轻量”有两个边界：

- 不追求完整复刻 SealDice
- 只 fake 当前测试真正需要的外部接口

### 总体结构

建议拆成三层：

1. 现有插件脚本层
   继续保留 `triangle-agency.ts` 作为最终上传到 SealDice 的主脚本。

2. 可测试逻辑层
   提取出与运行时解耦的核心逻辑，例如：
   - 投掷状态推进
   - QA 调整
   - 混沌结算
   - 三重升华分支处理

3. 测试驱动层
   提供一个最小 fake 环境，负责：
   - 记录角色卡属性读写
   - 记录群变量读写
   - 记录回复消息
   - 注入固定骰点结果

## 推荐测试技术

第一阶段推荐使用：

- Node 自带 `node:test`
- Node 自带 `assert/strict`
- TypeScript 编译

这样做的原因是：

- 当前仓库已经有 `typescript`
- 不必一开始就引入 `vitest` 或 `jest`
- 依赖少，后续维护成本低

如果后面测试规模变大，再升级到 `vitest` 也不迟。

## 文件设计

第一阶段建议新增以下文件：

- `triangle-agency/core.ts`
  - 放可测试的核心流程逻辑
- `triangle-agency/core.test.ts`
  - 首批流程测试
- `triangle-agency/fake-runtime.ts`
  - 最小 fake runtime
- `triangle-agency/tsconfig.test.json`
  - 测试专用 tsconfig

现有文件的职责保持为：

- `triangle-agency/triangle-agency.ts`
  - 负责插件注册、命令绑定和运行时接线
- `shared/seal.d.ts`
  - 继续只做类型声明

## 提取边界

为了避免测试代码直接强耦合到整个脚本文件，建议先提取下面这些边界清晰的逻辑：

### 1. 投掷状态数据结构

保留 `RollState` 的概念，但把它移动到可测试模块中。

这部分应包含：

- 当前投掷类型
- 骰点序列
- 成功数
- 混沌数
- 过载数
- 当前属性
- 当前阶段

### 2. 状态推进函数

建议把状态流拆成几个明确函数，而不是只能通过命令入口间接触发：

- 创建一次新投掷状态
- 应用过载
- 进入三重升华
- 进入 QA
- 执行 QA 调整
- 结算结果
- 结算混沌

### 3. 外部依赖抽象

把以下运行时能力抽象成接口，让 fake runtime 和真实 runtime 都能实现：

- 读取角色属性
- 写入角色属性
- 读取群变量
- 写入群变量
- 发送回复消息

随机数也要从 `Math.random()` 中抽出来，改成显式传入的骰点或骰点生成器。

## 第一批测试范围

第一批测试不追求全覆盖，只抓高风险路径。

### A. QA 正常结算

验证点：

- 属性检定在非三重升华时进入 QA
- `.taqa <数值>` 会正确扣除对应属性
- 成功数和混沌数同步变化
- 最终结果按调整后的状态结算

### B. QA 资源不足时拒绝调整

验证点：

- 当调整量大于当前属性值时，不应扣除属性
- 应返回“资质保证不足”提示
- 状态应继续保留，等待后续输入

### C. `taqa quit` 直接结算

验证点：

- 放弃调整时应立即按当前状态结算
- 结算后状态被清除

### D. 过载先于 QA 生效

验证点：

- 当属性值小于等于 `0` 时，先归零并 `过载 +1`
- 之后再进入后续流程
- 最终显示中要反映这次过载增加

### E. 三重升华分支不走普通 QA

验证点：

- 原始投掷 `Tri = 3` 时进入 `trine_select`
- 不进入普通 QA
- 在三重升华状态下，混沌不应按普通流程直接落账

### F. 新投掷打断旧 QA 状态

验证点：

- 若旧状态停在 QA，新的 `.ta` / `.tr` 会打断旧状态
- 旧状态应按“当前数值直接生效”去结算混沌
- 新状态应成功覆盖旧状态

### G. 新投掷打断三重升华状态

验证点：

- 若旧状态停在三重升华选择阶段，被新投掷打断时不应错误计入混沌

## 暂不纳入第一批的内容

以下内容可以以后再补，不放在第一阶段里：

- 风味文字模板渲染细节
- `.taflavor` 的完整管理行为
- `.tas` / `.tcs` / `.tcst` 的界面输出排版
- 插件注册和 `.set ta` 模板注册
- 全量命令级集成测试

这样可以把第一阶段聚焦在真正最危险的逻辑上。

## 兼容性与风险

### 风险 1：提取逻辑时引入行为偏移

如果把核心逻辑从 `triangle-agency.ts` 中搬出来时不够克制，可能把现有行为改坏。

应对方式：

- 第一阶段只提取最小必要逻辑
- 插件层仍然调用同一套核心函数
- 提取前后先跑 `typecheck`

### 风险 2：fake runtime 过于理想化

如果 fake runtime 设计得太“聪明”，可能让测试在 fake 环境里通过、在真实运行时里失败。

应对方式：

- fake runtime 只实现最少接口
- 尽量贴近现有变量读写方式
- 不在 fake 层加入额外业务逻辑

### 风险 3：测试只覆盖 happy path

状态机类 bug 往往出在中断、资源不足、顺序变化这些边缘路径。

应对方式：

- 第一批测试优先覆盖中断与失败路径
- 把“新投掷打断旧状态”列为首批必测项

## 成功标准

当第一阶段完成时，应满足：

- 可以通过单条命令运行 `Triangle Agency` 的自动测试
- 首批高风险流程测试稳定通过
- 以后新增规则调整时，可以先写失败测试再改逻辑
- 后续如果要补 `WuJing` 测试，可以复用同样模式

## 下一步

设计确认后，进入实现计划阶段。

实现时建议遵循：

- 先写失败测试
- 再做最小提取
- 最后把插件入口接回新的核心逻辑
